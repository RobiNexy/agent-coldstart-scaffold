# AI 助手工作流规则

## 每次会话的标准流程

### 阶段 1：加载上下文

按 [[AI-AGENT-START-HERE]] 指定顺序读取必读文件，简报状态并确认本次任务。

### 阶段 2：理解意图

- 主动澄清歧义，每轮聚焦 2–3 个关键问题。
- 新需求先确认对应的当前目标，必要时新增目标。
- 续做任务从 [[task-board]] 的 In Progress 或 Ready 选择任务卡。

### 阶段 3：起草或更新规格

- 新功能在 `feature-specifications/` 新建结论明确的规格文件。
- 修改已有功能时更新对应规格。
- 架构选择先形成 ADR 草案并请人类确认。
- 大任务拆成 Ready 或 Backlog 中可追踪的任务卡。

### 阶段 4：写测试与代码

- 先写测试，再实现；按一次垂直切片推进。
- 单次改动尽量不超过 5 个文件；超出时说明原因并分批。
- 新增或修改源文件时维护意图块：`@purpose`、`@invariants`、`@spec`、`@adr`、`@touches`。

### 阶段 5：自动验证

运行相关测试、类型检查与 lint。失败时定位并修复；无法修复时如实说明。

### 阶段 6：会话结束协议（强制）

结束对话前必须：

1. 更新 [[current-project-state]]：将关键变更置顶，最多保留 5 条。
2. 更新 [[task-board]]：移动完成任务，更新进行中进度，并记录发现的新任务。
3. 如有架构决策，创建 ADR；如有未决问题，追加到 [[open-questions-awaiting-human]]。
4. 检查本次修改文件中的 `[[...]]` 目标均存在。
5. 向人类输出变更简报。

影响面搜索统一使用 ripgrep（`rg`），例如 `rg -n -F '[[adr-filename' .`；不要改用 `grep`。

### 变更简报格式

```markdown
## 本次变更
- 影响：功能 / 规格 / 代码文件数 / 新 ADR

## 需要你决策的点
- [ ] 问题；如有临时建议，说明理由

## 我不确定的地方
- 风险或尚未验证的假设

## 下一步
- task-board 已更新；建议下次从……开始
```

简报控制在 200–500 字，突出人类需要 review 或裁决的内容。

## 必须先征求人类意见

- 修改数据库 schema，尤其删除列或改变类型。
- 破坏性修改对外 API，或违反已接受的 ADR。
- 引入新的外部依赖、服务或持续成本。
- 涉及付费、发邮件或生产环境三方调用。
- 删除超过 3 个文件。

## 可自主执行

- 不影响接口的内部重构。
- 修复 bug 并补充回归测试。
- 更新文档、日志和 metrics。
