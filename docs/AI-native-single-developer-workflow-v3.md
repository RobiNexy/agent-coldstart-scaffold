# AI Native 单人全栈项目工作流设计（v3）

> 版本：v3 存档版（取代 v2）
> 适用：单人开发者 + Coding Agent（LLM）长期维护全栈项目

## v2 → v3 变更摘要

1. 新增能力激活体系：人类维护能力包与路由表，LLM 负责路由执行并记录激活观测。
2. 全脚手架去角色化：以明确的能力簇描述认知操作，不用“你的角色”塑造输出。
3. 类型、测试、意图块成为三道互补验证防线，并补入语言无关的类型法则。
4. 测试意图块通过 `@spec` 回链，测试覆盖可用一条 ripgrep 查询。
5. 类型检查、测试、lint 三绿才算任务完成。
6. 人类新增第四个输入口：手工制作、维护能力包与路由表。

## 一、核心理念

单人 + LLM 场景下，重写代码的成本低，规格与决策更值得保留；文档的第一读者是 LLM；模块边界应以安全修改所需的上下文文件来判断；迭代粒度是对话级。

| 矛盾 | 应对 |
|---|---|
| 需求会变 | 规格锚定意图；用可逆性排优先级 |
| 人类带宽远小于机器带宽 | 分层视图、主动上报、决策点拦截 |
| 新会话无记忆 | 项目自解释化，以固定入口冷启动 |

### 1.1 角色指派与能力激活

面向 LLM 的项目指令采用能力激活式表述，不使用角色指派式表述。

| 维度 | 角色指派 | 能力激活 |
|---|---|---|
| 作用机制 | 让输出分布像某类人 | 命名具体要执行的认知操作 |
| 组合性 | 容易互斥 | 多个能力簇可叠加 |
| 退化模式 | 表演人设、术语正确但判断平庸 | 能力簇遗漏，可由路由系统补全 |
| 与规则系统 | 可能与制度冲突 | 能力管“怎么想”，规则管“怎么协作” |
| 本质 | 剧本 | 认知设置与认知诚实契约 |

v1/v2 的入口曾以“你的角色”开场；v3 修正这一点，原则对脚手架作者也适用。

## 二、命名原则

1. 目录名带用途，文件名带结论；可以长，不能含糊。
2. 知识文件名是全局唯一 ID，作为 `[[...]]` 引用目标。
3. 统一 kebab-case，禁用 snake_case / CamelCase。
4. 禁止用隐藏目录放知识资产。
5. 全大写文件名表示入口信号：`AI-AGENT-START-HERE.md`、`HOW-TO-USE-THESE-PROMPTS.md`。
6. 能力包文件名由人类决定，建议使用“领域-能力本质”形式。

## 三、目录结构

```text
项目根/
├── AI-AGENT-START-HERE.md
├── agent-knowledge/
│   ├── onboarding/                         # 启动盘与高频活文件
│   ├── capability-prompts/                 # 人类维护能力包、路由表和激活日志
│   │   ├── HOW-TO-USE-THESE-PROMPTS.md     # 人类维护、LLM 执行
│   │   ├── capability-activation-log.md    # LLM 只追加
│   │   └── [人类制作的能力包].md
│   ├── feature-specifications/
│   ├── api-contracts/
│   ├── data-model-specifications/
│   ├── architectural-decision-records/
│   └── operations-runbook/
├── src/
├── tests/
└── e2e-scenarios/
```

`capability-prompts/` 对脚手架是部分不透明的：脚手架提供路由说明和激活日志，不提供能力包模板、不检查能力包格式，也不附带代写的能力包正文。人类把自行维护的包放入该目录。

## 四、能力激活体系

### 4.1 所有权与纯净性

- 人类用元提示词工作流手工生成、命名、维护能力包，并维护路由表。
- LLM 对能力包与路由表只读、只路由；唯一可写文件是 `capability-activation-log.md`，且仅允许追加事件行。
- 脚手架不要求能力包 front matter、固定结构或格式，不提供能力包模板，也不检查包内容。
- 能力包内部是否使用 `[[...]]`、是否包含触发器，均由人类决定。
- 找不到匹配包时，LLM 在 open questions 中提出触发场景与期望能力簇；由人类决定是否制作，LLM 永不代写能力包。

能力包是认知协议，其有效性依赖人类对元提示词回路的控制；模板化可能稀释手作协议的密度。

### 4.2 路由机制

路由表位于 `agent-knowledge/capability-prompts/HOW-TO-USE-THESE-PROMPTS.md`，由人类维护。

加载优先级：

1. **人类点名**：立即加载。
2. **自动路由**：任务类型明确后按路由表选择，报告后生效。
3. **无匹配**：使用基础能力执行，不阻塞；简报记录“无匹配能力包”。

规则：

- 加载后必须说：“已加载 [包名]，将按其认知协议执行。”此确认句让路由生效可观测。
- 同时激活最多 3 包，避免上下文被能力提示稀释。
- 中途换任务时卸载不适用包，重新路由并再次确认。
- 冲突优先级：START-HERE 硬规则 > 能力包 > 脚手架默认行为。
- 能力包通过文件加载，不依赖特定 Agent 产品的 system prompt 机制。

### 4.3 激活观测

| 层 | 载体 | 频率 |
|---|---|---|
| 实时信号 | 激活确认句 | 每次加载 |
| 会话级 | 简报中的“激活的能力包”字段 | 每次会话 |
| 累积数据 | `capability-activation-log.md` | 每次会话追加一行 |

日志字段：

```text
日期 | 任务简述 | 激活的包 | 路由方式（点名/自动/无匹配） | 结果备注
```

日志是人类元提示词迭代回路的观测接口，可识别死包、自动路由与人类期望的偏差，以及激活包后任务是否受阻。熵增整理时压缩归档旧日志并报告统计；人类据此迭代能力包和路由表。

### 4.4 与脚手架的接线

- 阶段 2：任务明确后执行路由。
- 阶段 5：能力包的额外验证纪律纳入三绿门禁。
- 阶段 6：追加激活日志并在简报列出包名和路由方式。
- 能力包归纳触发器产生的结论必须落盘：ADR 候选进入 ADR 草案，行动项进入 task-board，风险与未决进入 open questions。不得只留在对话里。

## 五、统一引用规范 `[[...]]`

### 5.1 语法与方向

使用 `[[filename]]` 或 `[[filename|显示文字]]`，不带路径和扩展名。知识文件名必须全局唯一。文档到文档、代码到文档、测试到规格使用 `[[...]]`；文档到代码使用带路径的行内代码；代码到代码使用语言原生 import。

### 5.2 禁用项与检查

不使用 aliases、block references、embed 或 `#tag`。影响面和测试覆盖查询使用 ripgrep（`rg`）：

```bash
rg -n -F '[[0003-use-redis-optimistic-lock' AI-AGENT-START-HERE.md agent-knowledge/ src/ tests/
rg -l -F '[[feature-cancel-order-with-refund' tests/
```

第一条查询引用决策的文档、代码和测试；第二条列出回链到该规格的测试文件，结果为空表示该规格尚无回链测试。会话结束时检查本次涉及文件的悬空链接；整理时全量检查；重命名时全局更新。

## 六、代码与测试意图块

源文件示例：

```typescript
/**
 * @purpose 处理订单创建：库存扣减 → 订单落库 → 发起支付
 * @invariants
 *   - 订单创建是原子操作：要么完整成功，要么完全回滚
 *   - 库存扣减必须先于订单落库
 * @spec [[feature-place-order-with-inventory-lock]]
 * @adr [[0003-use-redis-optimistic-lock-for-inventory]]
 * @touches [[feature-payment-callback-idempotency]]
 */
```

测试文件示例：

```typescript
/**
 * @purpose 验证订单创建的业务行为
 * @spec [[feature-place-order-with-inventory-lock]]
 * @covers 库存不足返回 409 / 原子性 / 并发扣减
 */
```

| 字段 | 必填条件 | 说明 |
|---|---|---|
| `@purpose` | 源文件与测试文件 | 一句话说明用途 |
| `@invariants` | 核心业务文件 | 修改前必须理解的约束 |
| `@spec` | 业务源文件与测试文件 | 规格引用；测试通过它回链 |
| `@adr` | 涉及架构决策时 | 决策溯源 |
| `@touches` | 存在非局部影响时 | 波及面索引 |
| `@covers` | 测试文件 | 简述所覆盖的验收行为 |

## 七、三道验证防线

### 7.1 总览

| 防线 | 时机 | 捕获的问题 | 作用 |
|---|---|---|---|
| 类型 | 编译/静态检查 | 数据形状错误、非法状态 | 自动护栏；类型签名提供接口契约 |
| 测试 | 运行时 | 行为回归、边界条件 | 可执行规格与自我修复判据 |
| 意图块 | LLM 加载上下文时 | 误解意图、破坏不变式、遗漏依赖 | 跨文件影响索引 |

三者互不替代：类型表达不了行为，测试表达不了设计理由，意图块本身没有自动验证机制。

### 7.2 类型法则

1. **逃逸口 = 债务**：例如 TS `any`/`as`、Python 无注解函数、C `void*`、Go `interface{}`、Java raw type。必须使用时写 why、加 `TODO(types)` 并在简报说明。
2. **边界必验**：HTTP 入口、消息消费、事件 payload、数据库行等边界必须有运行时 schema 验证；验证失败即拒绝进入内部逻辑。
3. **非法状态不可表示**：优先 branded type、判别联合、newtype；状态不使用任意 string，金额使用有单位的整数分而非裸 number。
4. **strict 工具链强制**：如 TS `strict: true`、pyright/mypy strict、C/C++ `-Wall -Wextra`；配置须进仓库。
5. **类型优先作为意图载体**：能进入类型系统的不依赖注释；载体优先级为类型 > 测试 > 命名 > docstring > 内联注释。

### 7.3 测试法则

1. 测试意图块必须用 `@spec` 回链，覆盖关联可用 `rg` 查询。
2. 每条规格验收标准至少映射一个测试。
3. 行为变更测试先行：先表达新期望，再改实现。
4. 测试名描述行为，不以方法名代替行为。

### 7.4 意图块与注释法则

- 有价值的注释：why、非局部影响（优先 `@touches`）、TODO/FIXME。
- 禁止复述代码、记录版本历史、装饰性分隔线和没有测试支撑的行为承诺。
- 注释密度不均匀是预期：核心业务逻辑较密、CRUD 极少、胶水近零。

### 7.5 验证门禁

类型检查 + 测试 + lint 三绿才算任务完成；任一红色都不得进入结束协议。能力包的额外验证也纳入门禁。项目若尚未配置相应工具，应先完成工具链配置任务，不能把“未运行”当作通过。

## 八、任务看板与四文件分工

| 文件 | 回答的问题 | 时间视角 |
|---|---|---|
| `project-purpose-and-scope.md` | 为什么存在、边界在哪 | 长期 |
| `current-project-state.md` | 系统现在是什么样 | 现在 |
| `task-board.md` | 接下来做什么 | 将来 |
| `open-questions-awaiting-human.md` | 什么悬而未决 | 待裁决 |

任务粒度以一次会话可完成的垂直切片为宜；In Progress ≤ 2；Ready 必须自包含；短生命周期任务不编号；整理时清空 Done，git 历史负责归档。能力缺口建议写入 open questions，包含触发场景与期望能力簇。

## 九、关键指引文件

### 9.1 START-HERE 能力簇

新会话从根目录 START-HERE 进入：激活上下文自举、规格同步、决策遵从、能力包路由、三绿验证与认知诚实；按序读取 onboarding 必读文件，再根据任务读取路由表和匹配能力包。START-HERE 硬规则不能被能力包覆盖。

### 9.2 会话流程

1. 加载上下文并简报。
2. 澄清意图、路由能力包。
3. 起草/更新规格与 ADR。
4. 先写测试，再写代码；维护源文件和测试意图块。
5. 类型、测试、lint 三绿。
6. 更新状态、看板、问题、ADR、激活日志，持久化能力包触发器结果，输出简报。

### 9.3 编码约定

维护语言无关类型法则、测试回链规则、注释规范、引用格式与技术栈强制约束。项目选定技术栈后，将 strict 检查落实到实际构建配置。

### 9.4 能力包路由表

由人类维护的路由表只登记真实存在的包。LLM 读取并执行，不编辑路由或包正文。包内容不透明，脚手架不规定结构。激活日志由 LLM 每次会话追加一行。

### 9.5 ADR

ADR 文件名包含结论，记录背景、决策、理由、后果、重评条件和影响面。影响分析用 `rg -n -F '[[ADR文件名' .`。

## 十、人机交互接口

### 10.1 人类的四个输入口

1. 高层意图：对话或修改项目目的与范围。
2. 关键裁决：回答 open questions 或确认 ADR。
3. Review：检查变更简报并要求调整。
4. 能力包：通过元提示词手工制作、放入能力区并更新路由表；LLM 只能建议，不能代写。

### 10.2 分层视图

| 层 | 内容 | 读者 |
|---|---|---|
| L0 | 一句话状态 | 人类 |
| L1 | 变更简报 | 人类 |
| L2 | 状态、看板、路由表 | 人机共读 |
| L3 | 规格、ADR、能力包全文 | LLM 为主 |
| L4 | 代码、测试、日志 | LLM |

## 十一、熵增管理

每 10 次会话、每周或人类提出整理时：归档已解决问题；压缩过时状态；清理 Done 并检查 Ready；复核 ADR；扫描代码/规格漂移和悬空链接；清理术语；压缩激活日志并在日志中保留归档日期范围、各包使用频率、自动路由偏差和无匹配任务类型；输出整理报告。熵增整理允许重整激活日志，但不得改写能力区其他文件。

人类基于激活日志迭代包内容和路由表，制作缺失能力包。这是脚手架外的元提示词回路，脚手架只提供数据，不背书或检查包质量。

## 十二、需验证的假设

| 假设 | 验证方式 |
|---|---|
| 会话结束协议能持续执行 | 玩具项目 × 5 次新会话检查文件实际变更 |
| 新会话约 2 分钟进入状态 | 计时并评估简报质量 |
| 激活日志可信 | 抽查日志与 git diff |
| In Progress ≤ 2 可执行 | 观察实际并行任务数量 |
| `[[...]]` 纪律可维持 | 统计悬空链接趋势 |
| 路由准确 | 比较自动路由与人类期望的偏差 |
| 激活有效 | 对比同类任务有包/无包结果 |
| 多包叠加不劣化 | 观察 2–3 包时项目文件召回是否下降 |

## 十三、盲区

- 多会话并发修改看板会冲突，默认单会话推进。
- 简报可能遗漏模型未意识到的风险，仍需人类抽查。
- 能力包与 Agent 产品自带 system prompt 的叠加效应不可完全预测；换工具/模型需重新观测。
- 提示词对模型版本敏感；激活日志腐化会切断观测回路。
- 包生成质量和路由表质量由人类维护，脚手架不检查、不背书。
- 纯文本 + ripgrep 面向单人项目；规模增长后再评估索引能力。

## 十四、启动清单

1. 建立 onboarding、capability-prompts 和规格分类目录。
2. 起草能力激活式 START-HERE、协作规则与编码约定。
3. 由人类填写项目目的、范围和关键边界。
4. 建立状态、看板、open questions、glossary 与激活日志。
5. 人类制作首批能力包并维护路由表；能力包不由 LLM 生成。
6. 初始化并提交 git，验证新会话能正确简报和路由。
7. 建立 strict 类型检查、测试、lint 工具链，再开始最小垂直切片。
8. 五次会话后整理并回顾路由和激活效果。

人类必须原创的核心内容：项目方向与边界、关键决策裁决、能力包及路由表。其余由 LLM 起草、人类 review。
